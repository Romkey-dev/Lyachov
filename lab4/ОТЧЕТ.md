## Часть 1: Статический анализ кода (SAST) с Bandit {#часть-1}

**Инструмент:** Bandit — Python SAST-сканер  
**Приложение:** Flask User Management API  
**Стек:** Python 3, Flask, SQLite

### Структура проекта

```
lab13-sast/
├── vulnerable_app.py
├── secure_app.py
├── test_apps.py
├── requirements.txt
├── .bandit
└── run_analysis.py
```

### Уязвимости в исходном коде

| Строка | Код Bandit | Уязвимость | Серьёзность |
|---|---|---|---|
| `API_KEY = "demo_training_key_example"` | B105 | Hardcoded password | Low |
| `app.run(debug=True)` | B201 | Flask debug mode | High |
| `subprocess.check_output(cmd, shell=True)` | B602 | shell=True + user input | High |
| `f"SELECT id, username, email FROM users WHERE id = {user_id}"` | B608 | SQL Injection | Medium |
| `f"SELECT id, username, email FROM users WHERE username LIKE '%{username}%'"` | B608 | SQL Injection | Medium |

### Исправления

#### A. SQL-инъекция → Параметризованный запрос

```python
cursor.execute('SELECT id, username, email FROM users WHERE id = ?', (uid,))
```

```python
cursor.execute('SELECT id, username, email FROM users WHERE username LIKE ?', (f'%{username}%',))
```

#### B. Hardcoded Secret → Переменная окружения

```python
API_KEY = os.environ.get('API_KEY')
if not API_KEY:
    raise EnvironmentError('API_KEY environment variable must be set')
```

#### C. Command Injection → Allow-list

```python
ALLOWED_COMMANDS = ['date', 'whoami', 'hostname']
if cmd not in ALLOWED_COMMANDS:
    return jsonify({'error': 'Command not allowed'}), 403
output = subprocess.check_output([cmd])
```

#### D. Flask debug=True

```python
debug_mode = os.environ.get('FLASK_DEBUG', 'false').lower() == 'true'
app.run(debug=debug_mode, host='0.0.0.0', port=5001)
```

### Запуск Bandit — После исправлений

```bash
python run_analysis.py
```

**Ожидаемый результат:** нет High/Medium уязвимостей в `secure_app.py`.

### Задание A: Анализ зависимостей (npm audit)

Исходные зависимости были установлены через `package.json`.  
Для анализа запускались:

```bash
npm install
npm audit
```

Затем выполнено исправление зависимостей через `npm audit fix` и проверка пакетов.

### Задание B: XSS-уязвимости

В уязвимом приложении `vulnerable_app.js` пользовательский ввод напрямую отправляется в HTML и SQL-запросы.

В защищённой версии `secure_app.js` выполнено:
- серверная санитизация данных перед сохранением
- безопасный вывод в шаблоне EJS через `textContent`
- установка CSP-заголовка
- запрет `innerHTML` для недоверенных данных

### Задание C: SQL-инъекция в Node.js

В `vulnerable_app.js` запрос сортировки формируется динамически без проверки:

```js
ORDER BY ${sort}
```

В `secure_app.js` добавлен allow-list:

```js
if (!ALLOWED_SORT.includes(sort)) {
  return res.status(400).json({ error: 'Invalid sort parameter' });
}
```

А поиск выполнен параметризованно:

```js
db.all('SELECT id, username, comment, created_at FROM comments WHERE comment LIKE ?', [`%${search}%`], ...)
```

## Сравнение инструментов {#сравнение}

| Характеристика | SAST (Bandit) | SCA (npm audit) | DAST (OWASP ZAP) |
|---|---|---|---|
| Что анализирует | Исходный код | Зависимости | Работающее приложение |
| Когда запускать | При каждом коммите | При установке пакетов | На staging/PR |
| Скорость | Быстро | Быстро | Медленнее |
| Ложные срабатывания | Средне | Низко | Средне |
| Находит | SQLi, XSS, insecure config | CVE в библиотеках | Конфигурации, runtime-уязвимости |
| Код нужен | Да | Нет, только manifest | Нет |

## Ответы на вопросы {#ответы}

**Q1: Какие уязвимости обнаружил Bandit?**  
B201 (Flask debug=True), B602 (subprocess shell=True), B608 (SQL-код внутри строк), B105 (hardcoded secret).

**Q2: Почему параметризованные запросы защищают от SQLi?**  
Потому что данные передаются отдельно от структуры SQL-запроса. Даже если пользователь отправляет `1 OR 1=1`, база воспринимает это как строку, а не как часть SQL.

**Q3: Разница shell=True vs shell=False?**  
`shell=True` передаёт строку оболочке, что позволяет использовать `;`, `&&`, `|` и выполнять произвольные команды. `shell=False` запускает программу напрямую, поэтому пользовательский ввод не разбивается и не интерпретируется оболочкой.

**Q4: Что SAST не обнаруживает?**  
Ошибки архитектуры, неправильную конфигурацию сервера, уязвимости в сторонних библиотеках и runtime-проблемы. Это задачи DAST и SCA.

**Q5: В чём разница npm audit vs Snyk?**  
`npm audit` использует базу NPM Advisory и встроенный анализ. `Snyk` предоставляет более глубокий анализ транзитивных зависимостей и расширенные рекомендации.

**Q6: Почему CSP эффективен против XSS?**  
Потому что браузер блокирует выполнение скриптов, которые не разрешены политикой. Даже если вредоносный код попал на страницу, он не выполнится без правильного источника или nonce.

## Общий вывод {#вывод}

Лабораторная работа показала, что для надёжной защиты требуются все три подхода:
- SAST находит уязвимости в коде до запуска;
- SCA выявляет уязвимые библиотеки и версии;
- DAST проверяет реальное приложение в runtime.

При построении DevSecOps-конвейера важно использовать Bandit, npm audit и динамическое сканирование вместе, чтобы покрыть разные уровни безопасности.
